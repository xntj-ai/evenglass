把 G2 智能眼镜接成 PC 外设这件事，
我做到一半放弃了

花了八天，做出了一条从 PC 命令到 G2 麦克风、再回到 PC 落盘 wav 的端到端链路。最后停下，不是因为做不动，而是因为这个产品形态对我个人不成立。这篇是给后来者看的复盘——已经踩过的坑、做出来的东西、以及为什么我没继续。

01缘起

想把 G2 当成 PC 的麦克风 + 显示外设

Even Realities G2 是一副带显示的智能眼镜，外观接近普通眼镜，但内置麦克风、触摸条、镜片可显示文字。原生体验绑定它自己的手机 App，做翻译/字幕/笔记。

我想要的不是这些。我想要的是：

  • 戴着眼镜，按住 CapsLock 说话，PC 上的输入法（voice-input）就把语音转成文字插入光标位置——眼镜代替桌面麦。
  • Claude Code 在终端里输出的关键日志、运行状态、AI 回答的开头——直接显示在镜片上，不用低头看屏幕。

本质上是把 G2 从一个"独立的小型计算机"重新定义成"PC 的瘦客户端外设"。手机和服务器只做透传，业务全在 PC 端跑。

为什么不让手机直接接 PC

G2 的 BLE 在音频侧的协议至今未公开，公开 SDK 只在手机里能跑（Android Hub App 容器形式）。绕开手机直接 PC ↔ G2 是死路。所以架构上手机这一层是无法跳过的——这是后面放弃的核心理由之一。

02架构

五层透传，业务都在 PC 端

[G2 眼镜]
↓ BLE (Even 私有协议)
[Android 手机 · Even Hub Web App]
↓ WSS (Phoenix Channel)
[北京服务器 · Phoenix/Elixir]
↑ WSS (双 token 双 role)
[Windows PC · 诊断工具/虚拟麦/voice-input]

每一层职责

层实现职责
G2原厂固件麦克风采集 / 镜片显示
手机Even Hub + 自写 Web App（TS）BLE 通信 / SDK 调用 / WSS 转发
服务器Phoenix 1.8 + LiveView 1.1认证 / 限流 / Channel 路由 / Admin 实时观测
PCRust + egui（诊断）/ 待写虚拟麦业务逻辑 / 用户交互

选 Phoenix 是因为：BEAM 进程模型对"几千个长连接 + 实时广播"几乎零摩擦；LiveView 让 admin 后台不用前后端分离就能做到 60 events/min 实时刷新；Channel 协议本身就是为这种场景设计的。Elixir 的代价是社区比 Node 小，但收益是工程量明显更小。

03做了什么

从 4-27 到 5-04，八天，五个里程碑

A · 4-27

数据模型 + Admin 实时事件流

sessions(device_id) + events(direction, type, payload jsonb) 双表。Sessions.touch_session_by_device_id! 走 atomic upsert，Events.create_event! 写完直接 broadcast 到 PubSub topic "events:all"。

/admin/events LiveView 流式 50 条，diff push 实时刷。压测 60 events/min 丝滑。

B · 4-27

真实 REST 端点

POST /api/g2/events（手机上报）+ POST /api/g2/commands（PC 下发）。/admin/devices + per-device 过滤。删 mock controller。

C · 5-02 → 5-03

生产级硬化

认证（phx.gen.auth + TOTP 强制注册门）+ 限流（Hammer 7.x ETS）+ 幂等（header keyed 去重）+ OpenAPI（open_api_spex）+ check_origin 配置。这块花了最多时间，做完之后服务端就是"生产可用"状态。

147 个 mix test 全过，部署到 g2.xntj.tv 上线。

D1a · 5-04

音频上行链路打通

Hub App 把 G2 麦克风的 PCM 帧按 100ms 窗口聚合成 base64，通过 channel push 上来。服务端是纯透传（PCM 是 live-or-never，丢了就丢，不存盘），但每秒写一条 audio_meta event 给 admin 面板看流量。

这一步的副产品是个意外的协议发现，下一节专门讲。

D1b · 5-04

双向控制面 + Rust 诊断工具

新增 pc_admin 角色 + 独立 token salt。Channel 上加 start_audio / stop_audio 命令，broadcast_from! 让 hub-app 收到、PC 自己不回环。

写了 tools/g2-mic-test/ Rust + egui 单窗口工具，~700 行，包含一个手写的 Phoenix V2 wire format 客户端（社区里 Rust 实现很少）。端到端验证：PC 点 Connect → 拿 socket-token → WSS join → 点 Start G2 mic → 收 PCM → 录 wav → 放出来听到自己说话的声音。

04关键技术发现

G2 上行不是 LC3，是裸 PCM

开始之前我读过几个 G2 协议逆向项目（包括 i-soxi/even-g2-protocol），大部分都假设 G2 麦克风走 LC3 编码（40 字节/10ms），所以我提前规划了 LC3 解码这一步。

D1a 跑通后第一时间看了 admin 面板的流量计数：

15:39:31  bytes=38400  frames=12  window_ms=1095  format=pcm_s16le
15:39:33  bytes=35200  frames=11  window_ms=1013  format=pcm_s16le
15:39:34  bytes=38400  frames=12  window_ms=1105  format=pcm_s16le
15:39:35  bytes=38400  frames=12  window_ms=1091  format=pcm_s16le

bytes / frames = 3200。16000 Hz × 2 byte/sample × 0.1 s = 3200。完美吻合 16kHz mono S16LE PCM、100ms 一帧。

结论

Even Hub SDK 在 simulator 上输出的 audioPcm 字段就是裸 PCM，不是 LC3。下游消费者不需要任何解码器，直接喂 ASR 即可。注意这只是 simulator 的实测，真机上是否一致需要真机验证（我没机会做）。

这个发现让 D1b 的工程量直接砍掉一半——本来还在算"加 lc3-rs 依赖、跑 wasm pack、性能测试"那一套，最后一行 LC3 代码都不用写。

05为什么放弃

三个理由，从弱到强

理由 1：开源生态还没成熟

G2 公开 SDK 只覆盖了 Even Hub 容器内的 Web App 这一种形态。要把眼镜接到任何其他系统，都得通过它的手机 App 中转。SDK 文档不全，sideload 入口在中文版 com.even.sg 里目前没有暴露。社区项目稀少，能找到的几个还停在 G1 时代或者只逆向了部分协议。

这意味着每一个想做 G2 二次开发的人，都得自己摸一遍这条路。我做了一遍，但没有意愿做"上游"——开源出来给后人用。

理由 2：手机中转是死结

正常一个 PC 外设的拓扑应该是：设备 → PC。中间多一跳手机，意味着：

  • 手机要常驻一个进程，电量是问题
  • 手机一断网整条链路都炸
  • 开发态要同时维护三个端（手机/服务器/PC），调试一次要刷三份
  • 用户使用前要装手机 App + 配账号 + 戴眼镜 + 开 PC 软件——心智负担太重

架构上的优雅没有办法补救体验上的笨重。除非未来 Even 开放 BLE 直连协议，否则手机这一跳是物理上拿不掉的。

理由 3：我不戴眼镜

这是最直接也最不"工程"的理由：我视力正常，平时不戴眼镜。G2 戴上之后鼻梁有压痕、镜腿压耳朵，超过两小时就明显不舒服。

当工具的物理形态自身就抵抗使用，再优雅的软件层都没救。voice-input + 桌面麦克风的组合对我而言没有任何痛点——CapsLock 一按、说话、出字，整个流程零摩擦。G2 要做到一样的体验，我得：

  • 戴上一个我本来不戴的东西
  • 开手机 App 保持后台
  • 开 PC 端虚拟麦桥
  • 开服务器（或者本地起 Phoenix）

四步换零步。即使做到极致，也是负优化。

决定停下的那一刻，是我装 VB-Audio Cable 之前——意识到下一步要写一个 600 行的 Rust 桥程序，让一个我不戴的设备替代一个我已经用得很顺的麦克风。这个交易不成立。

06给后来者

如果你正打算做类似的事

这套代码里值得偷的东西

  • Phoenix V2 wire format 的 Rust 实现（tools/g2-mic-test/src/channel.rs）。phoenix.js 自动加 /websocket 后缀和 vsn=2.0.0，raw client 不会，第一次写很容易踩。30s 心跳 + 5-tuple 帧格式都在里面。
  • 双 role socket 模型（device vs pc_admin 在同一个 UserSocket 用不同 clauses 分流，独立 token salt）。这种"一个 socket 跑两类客户端但权限完全隔离"的写法网上很少见。
  • TOTP 强制注册门（PCUserAuth.require_totp_enrolled/2）。第一次登录的 admin 必须先扫码绑 TOTP 才放行 /admin。phx.gen.auth + NimbleTOTP 大部分博客只讲到 QR 渲染，登录拦截这块要自己写。
  • Dockerfile 在中国大陆构建的优化。github.com 不可达 + hex.pm 慢，所以预先 vendor heroicons 和 tailwind 二进制，apt + hex 都换 Tencent/upyun 镜像。如果你在国内构建 Phoenix 应用，这个文件直接抄。

不要踩的坑

  • 不要默认 G2 上行是 LC3。 simulator 是 PCM。真机你自己测帧大小再决定是否要 LC3 解码。
  • 不要去改第三方项目的代码做集成。 我曾经想直接给 voice-input 加 Phoenix Channel client——这是错的。第三方项目的边界要尊重，要么写桥要么提 PR，不要 fork。
  • 不要自己写 Windows 虚拟音频驱动。 EV 证书 ~$200/年 + Microsoft Hardware Dev $99 + 内核编程 1-2 周。VB-Audio Cable 是免费的工业标准方案，3MB 装好直接出 CABLE Input/Output 两个设备。
  • 不要假设 sideload 可用。 写代码前先确认 hub 容器能装第三方 Web App。如果不能，你只能在 simulator 里跑，用户买回来的眼镜实际跑不通。
